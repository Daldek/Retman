# Retman a MCP — rekomendacja

- **Data:** 2026-10-19
- **Zakres:** czy i jak Retman ma używać MCP (Model Context Protocol): (a) pominąć MCP i zostać
  przy wywołaniach w procesie, (b) Retman jako *klient* MCP serwerów narzędzi, (c) Retman jako
  *serwer* MCP, (d) odłożyć. Dotyczy Kartografa 0.8.0 (`kartograf-mcp`) i IMGWTools 3.0.0
  (`imgw mcp`).
- **Metoda:** fakty sprawdzone w repozytoriach i przez uruchomienie serwerów narzędzi offline
  (Kartograf `d7b5369e`, IMGWTools `31e96fa`; pomiar opóźnień i rozmiarów `tools/list`, próba
  mechanizmu elicitation na SDK `mcp` 2.3.0 w pamięciowym `Client(server)`); rzeczy niesprawdzone
  oznaczone [WNIOSEK].
- **Status:** decyzja delegowana przez autora (2026-10-19) — decyzje autora 8 i 7: autor nie
  rozstrzygnął, **powierzył** decyzję badaniu, a rekomendacja stała się decyzją.

## Decyzje końcowe (zgodność z planem wdrożenia z 2026-10-19)

1. **MCP: w kodzie nic w v0.1** (decyzja 9 planu wdrożenia) — wyłącznie ADR i dokumentacja; zgodnie z
   rekomendacją poniżej (żadnego kodu MCP, zależności MCP ani klucza `[mcp]` w v0.1/0.2).
2. Handler ma teraz sygnaturę `handler(params, inputs, output_dir, ctx)` (decyzja 1 planu;
   `ToolContext`, `PlanClient`/`RunClient` — raport `2026-10-19-integracja-narzedzi.md`). Odwołania
   w p. 2 pkt 4 do `handler(params, inputs, output_dir) -> HandlerOutput` czytać z tym dodatkowym
   argumentem; wniosek („kontrakt handlera jest agnostyczny wobec transportu”) pozostaje w mocy.
3. Numer ADR: tu proponowane ADR-012; ostateczną numerację ADR przydziela Main (raport integracji
   mówi to samo).
4. Luka `Plan.from_dict` ufające `confirmed` (p. 5) jest potwierdzona także w raportach integracji i
   sprawdzania dostępności; naprawa przed jakimkolwiek zdalnym interfejsem, nie blokuje v0.1.

## 1. Rekomendacja (rozstrzygająca)

| Opcja | Werdykt | Kiedy |
|---|---|---|
| (a) Zignorować MCP, zostać przy wywołaniach Pythona w procesie | **PRZYJĄĆ w v0.1 i w każdej późniejszej wersji** jako sposób, w jaki Retman rozmawia z narzędziami | teraz |
| (b) Retman jako **klient** MCP serwerów narzędzi | **ODRZUCIĆ** (nie „odłożyć”: brak korzyści, realne koszty; zob. p. 2) | nigdy, chyba że zadziała wyzwalacz z 6.2 |
| (c) Retman jako **serwer** MCP (potwierdzone, audytowane plany dla zewnętrznych agentów) | **ZOSTAJE jak zaplanowano: v0.3** (PRD 9, ARCHITECTURE 7.5/11). Kontrakt projektowy poniżej zapisać teraz jako ADR-012. **Żadnego kodu MCP, żadnej zależności MCP, żadnego klucza konfiguracji `[mcp]` w v0.1/0.2.** | v0.3 |
| (d) Odłożyć | Dotyczy tylko (c); to istniejący harmonogram | — |

Jednozdaniowe podsumowanie do ADR: *Retman rozmawia z narzędziami przez ich API Pythona (nigdy przez
ich serwery MCP); sam staje się serwerem MCP w v0.3, jako opcjonalny dodatek, z potwierdzeniem
przez człowieka dostarczanym przez MCP elicitation i z zamknięciem awaryjnym, gdy klient go nie
potrafi pokazać.*

Nic w pracach v0.1 nie zmienia się z powodu MCP. Migrację do Kartografa 0.8.0 / IMGWTools 3.0.0
projektować wyłącznie na ich API Pythona / katalogu komend (to pytanie rozstrzygnięte osobno).

## 2. Dlaczego nie (b): Retman jako klient MCP

Dowody:

1. **Serwery MCP narzędzi to cienkie nakładki na te same wywołania biblioteki, które Retman już
   wykonuje.** Nagłówek `kartograf/mcp_server.py`: „Every tool calls one function of the library and
   returns the document that function's result serializes to”; `_data_tool` woła `validate_command`,
   potem `run_command` (API katalogu). IMGWTools `src/imgwtools/mcp/_calls.py` robi to samo nad
   `check_command/run_command/validate_command`. `run_command` w procesie zwraca identyczną kopertę
   (`kartograf-*/1`, `imgw-result/1`), te same kody błędów. MCP dodaje transport, nie dodaje możliwości.
2. **N-10 / ARCHITECTURE 9.3.** Zależności rdzenia to „tylko klient HTTP”. `mcp==2.3.0` to biblioteka
   protokołu, a nie SDK dostawcy modelu, więc *litera* N-10 (brak ML, brak SDK dostawców, brak
   basala) nie jest naruszona — ale łamie regułę 9.3 „Zależności podstawowe: minimalne — klient
   HTTP”. Zmierzone: rdzeń Retmana (`httpx`) + Kartograf + IMGWTools[store] = 33 dystrybucje; po
   dodaniu extras `mcp` = 56 (`httpx2`, `starlette`, `uvicorn`, `pydantic>=2.12`,
   `pyjwt[crypto]` → `cryptography`, `opentelemetry-api`, `sse-starlette`, `python-multipart`,
   `pywin32` na Windows). `httpx` 0.28 i `httpx2` 2.14 współistnieją (brak konfliktu resolvera;
   sprawdzone `uv run --with`). ADR-046 Kartografa zapisuje, że instalacja `mcp` podniosła `idna`
   3.11→3.20 (oznaka rotacji zależności). Klient potrzebowałby tego w rdzeniu albo jako dodatku,
   który musi zainstalować każdy użytkownik, plus dodatku `[mcp]` każdego narzędzia
   (`kartograf[mcp]`, `imgwtools[mcp,store]`) → gorsze `uv tool install --with` (N-09, ARCHITECTURE 9.4).
3. **W-05 / brak sieci przed potwierdzeniem (decyzja autora 4) stają się trudniejsze, nie łatwiejsze.**
   - `imgw mcp` startuje w trybie odczytu: komendy zapisujące są *wymuszane* na `check: true`
     (tylko plan); zapis wymaga `imgw mcp --allow-writes` i nadal `check: false` per wywołanie
     (IMGWTools AGENTS.md l.35, ADR-004 D7). Retman musiałby uruchomić drugi proces serwera z
     zapisem po `plan.confirm()`, czyli logikę cyklu życia procesu dla bramki, którą już posiada.
   - `kartograf-mcp` nie ma żadnej bramki zapisu (`elevation_download` ma `readOnlyHint=false,
     destructiveHint=false, openWorldHint=true`, zmierzone przez `tools/list`); reguły ścieżek to
     `--allow-dir` (tylko ścieżki bezwzględne, `mcp_server.py:382-405`) — druga warstwa polityki
     ścieżek obok reguły `output_dir` Retmana (ARCHITECTURE 3.2.4 reguła 5).
   - `elevation_availability`, `check_updates`, `stations_find` (source=live), `store_check` itd. to
     narzędzia sieciowe przez MCP dokładnie tak jak w procesie; MCP nie rozwiązuje decyzji 4.
4. **Kontrakt handlera jest już agnostyczny wobec transportu** (`handler(params, inputs, output_dir)
   -> HandlerOutput`, `retman/adapters/manifest_adapter.py:35`; patrz decyzja końcowa 2). Handlery
   wykonują w procesie obróbkę, której wynik MCP nie wspierałby czysto: walidacja `Path` → `kind`,
   `_extract_shapefiles` (`retman/tools/kartograf/handlers.py:163`), typowane wyjątki, postęp.
   Nic w rdzeniu nie musiałoby się zmienić, gdyby jeden handler *kiedykolwiek* użył innego transportu
   — więc (b) można przyjąć per handler później bez decyzji architektonicznej teraz.
5. **Opóźnienie (zmierzone na tej maszynie, Kartograf `d7b5369e`, IMGWTools `31e96fa`):**
   `import kartograf` w procesie 1,19 s (płacone raz, leniwie, po potwierdzeniu — ARCHITECTURE
   3.2.5 krok 3); uruchomienie `kartograf-mcp` + `initialize` 1,26 s; `imgw mcp` 0,93–1,49 s;
   jedno trywialne wywołanie 0,07 s. Nie rozstrzygające (≈ równe importowi w procesie), ale to
   czysty narzut plus proces potomny na narzędzie do nadzorowania (anulowanie, osierocone procesy;
   obiekty zadań `pywin32` na Windows [WNIOSEK]).
6. **Schematy to zła rzecz do podania małemu modelowi.** Ładunek `tools/list`: Kartograf 29 narzędzi
   34,5 KB, IMGWTools 37 narzędzi 50,9 KB JSON Schema (~85 KB ≈ >20 tys. tokenów [WNIOSEK: 4
   znaki/token]). Projekt Retmana (ARCHITECTURE 3.2.3 „dokumentacja nie jest czytana w trakcie
   działania”, 1.1 „liczby liczy kod”, 5.3 zamknięte listy) istnieje właśnie po to, by tego unikać.
   IMGWTools sam formułuje wniosek: ADR-004 D11 „Retman — bez wymaganych zmian … MCP nie jest mu potrzebny”.
7. **Testowalność:** dziś testy handlerów uruchamiają prawdziwą bibliotekę offline
   (`tests/tools/kartograf`). Ścieżka klienta MCP potrzebuje uruchomionego serwera albo transportu
   w pamięci plus dodatków `[mcp]` obu narzędzi w środowisku testowym. Ściśle gorzej niż
   monkeypatch wywołania Pythona.

Co Retman *powinien* wziąć z prac nad MCP, niezależnie od MCP: **katalogi/schematy** narzędzi są
źródłem szkiców `retman-scaffold` i kontroli dryfu (to pytanie o katalog, rozstrzygnięte osobno,
raport `2026-10-19-integracja-narzedzi.md`; dane są w `command_schema()` / `catalog`, a nie w
serwerze MCP).

## 3. Dlaczego (c) pozostaje wartościowe, ale nie w v0.1

Wartość (dlaczego zachować): ogólny agent (Claude Code itp.) już dziś może sterować serwerami MCP
narzędzi bezpośrednio. Czego od nich nie dostanie, a Retman może dać:

- wykonanie potwierdzone przez człowieka z **planem pokazanym z proweniencją** (W-04/W-05), zamiast
  pytań hosta per wywołanie narzędzia (serwer Kartografa nie ma żadnej bramki zapisu);
- **ślad audytowy W-15** w folderze projektu (`result.json`, `journal.jsonl`) łącznie z decyzjami
  modelu, sumami kontrolnymi, środowiskiem;
- **ponumerowaną przestrzeń roboczą** (S-02, ARCHITECTURE 5), walidację `kind`, wyniki zamknięte w
  `output_dir`;
- zamknięte listy/ekstraktory (W-02) i polskie teksty.

Nie jest wyróżnikiem Retmana przez MCP: rozumienie języka naturalnego. Agent frontier rozumie język
naturalny lepiej niż basal i przekazuje ustrukturyzowane argumenty; dla agentów zewnętrznych Retman
jest więc **bezpiecznym, audytowanym wykonawcą**, a krok NL jest przypadkowy. Dlatego (c) jest
decyzją produktową v0.3, a nie potrzebą v0.1; PRD 3.2 (prosta ścieżka: nieprogramiści, mały model
lokalny, własne okno czatu) obsługuje CLI/czat, a PRD 9 już wymienia „0.3 — dostęp przez MCP (np. z
innych asystentów AI)”.

Dlaczego nie wcześniej niż 0.3: v0.1 niesie już Kartografa 0.8.0 + całe IMGWTools; MCP dodaje
opcjonalny dodatek, problem kanału potwierdzenia (4.2) i powierzchnię prywatności (4.5), które
potrzebują własnych testów.

## 4. Dokładny kontrakt dla (c) — zapisać w ADR-012, wdrożyć w v0.3

### 4.1 Pakietowanie

- Moduł `retman/mcp_server.py` (leniwy import SDK; `import retman.mcp_server` działa bez `mcp`, jak
  `kartograf.mcp_server`, którego `create_server`/`main` drukują wskazówkę instalacji).
- Opcjonalny dodatek: `retman[mcp] = ["mcp>=2.3,<3"]` (ten sam pin co oba narzędzia → brak rozłamu
  resolvera). **Nigdy** w `dependencies`. `retman[dev]` go dostaje, by testy mogły działać. Zależności
  rdzenia zostają `["httpx>=0.27"]`.
- Punkt wejścia: `retman mcp --project <dir>` (podkomenda, jak `imgw mcp`; bez dodatkowego skryptu
  konsolowego). Tylko stdio w 0.3; Streamable HTTP czeka na API HTTP (0.4) i jego model uwierzytelniania
  (IMGWTools podjęło tę samą decyzję: brak zapisów przez HTTP, ADR-004 D9).
- `--project` jest **wymagane**, bez domyślnego cwd (klient wybiera cwd serwera — ta sama lekcja co
  docstring `kartograf.mcp_server.default_cache_file`; a N-11 zabrania ukrytej wartości domyślnej).
- Linia w dokumentacji instalacji: `uv tool install "git+https://github.com/Daldek/Retman@vX" --with "mcp>=2.3,<3"`
  (lub `retman[mcp]`); konfiguracja klienta: `{"mcpServers":{"retman":{"command":"retman","args":["mcp","--project","/abs/dir"]}}}`.
- Windows/Linux/macOS: SDK wspiera wszystkie (`mcp/os/win32`, zależność `pywin32`); dodać dodatek do
  macierzy czystej instalacji w CI (ARCHITECTURE 9.4 „Sprawdzanie w CI”) od 0.3.

### 4.2 Narzędzia (cienka nakładka na publiczne API z ARCHITECTURE 7.1 — bez nowej powierzchni potoku)

Cały stan po stronie serwera mieszka w pamięciowej mapie `plan_id → Plan` (nieprzezroczysty id, TTL,
ograniczona). **Nigdy nie deserializować planu przysłanego przez klienta**: `Plan.from_dict`
odtwarza `confirmed` ze stanu (`retman/core/plan.py:152`), więc zserializowany słownik mógłby nieść
`confirmed=true`.

| Narzędzie | Adnotacje | Zachowanie |
|---|---|---|
| `retman_operations` | readOnly, !openWorld | lista operacji zainstalowanych narzędzi: id, polska etykieta, parametry, `kind`y (z manifestu) |
| `retman_plan(command: str, known?: object)` | readOnly | `Retman.plan(command, known)`; zwraca `{plan_id, plan: Plan.to_dict(), summary: plan.summary()}`. Wartości przekazane przez agenta w `known` są pokazywane ze źródłem `known`. Woła skonfigurowany backend decyzyjny (bez sieci narzędzi). |
| `retman_answer(plan_id, name, answer)` | readOnly | `plan.answer(name, answer)`; zwraca nowy plan (łącznie z otwartymi `questions`) |
| `retman_execute(plan_id)` | `readOnly=false, destructive=false, openWorld=true` | **jedyna** ścieżka wykonania; patrz niżej |
| zasoby `retman://results`, `retman://results/{n}` | — | `result.json` projektu (co jest ukryte: p. 4.5) |

`retman_execute` (niezmiennik W-05):

1. Plan musi istnieć i nie mieć otwartych pytań (inaczej `PlanIncompleteError`).
2. Serwer pyta **człowieka** przez MCP elicitation (spec 2026-07-28: narzędzie zwraca
   `InputRequiredResult` z `ElicitRequestFormParams`; niskopoziomowy `Server.on_call_tool` wspiera to
   w `mcp` 2.3.0) z **pełnym polskim podsumowaniem planu** (`plan.summary()`, wartości
   domyślne/przestrzeń robocza/`known` oznaczone) i polem logicznym `confirm`.
3. Dopiero przy `action == "accept"` z `confirm == true` dla *tego* planu serwer woła
   `plan.confirm()`, potem `retman.execute(plan)`. Odmowa/anulowanie → dziennik `plan odrzucony`,
   wynik błędu.
4. **Zamknięcie awaryjne:** jeśli klient nie zadeklarował zdolności elicitation (lub odpowiedź jest
   czymkolwiek innym), brak wykonania; zwracany błąd `confirmation_unavailable` z podsumowaniem planu
   i instrukcją uruchomienia w terminalu (`retman`) lub użycia klienta wspierającego elicitation.
   `retman_plan`/`retman_answer` nadal działają (podglądy tylko do odczytu).
5. Agent nigdy nie może ustawić potwierdzenia: nie ma argumentu `confirm`, nie ma przełącznika w
   konfiguracji (ARCHITECTURE 6.3: „Nie ma trybu, który je pomija”).

Dowód offline, że mechanizm działa (uruchomione 2026-10-19 z `mcp` 2.3.0, pamięciowy
`Client(server)`): accept → narzędzie zadziałało (1 wykonanie); decline → `is_error`, brak wykonania;
klient bez wywołania zwrotnego elicitation → błąd klienta i brak wykonania. Kod produkcyjny musi
sprawdzać zdolność jawnie, a nie polegać na tym błędzie [WNIOSEK: dokładne API sprawdzania zdolności
do potwierdzenia w 0.3]. Czy Claude Code i inni klienci implementują przepływ elicitation/MRTR z
2026-07-28 jest **niesprawdzone** [WNIOSEK]; wykonać test dymny przed obietnicą i zachować regułę
zamknięcia awaryjnego niezależnie.

### 4.3 Pytania (W-02) przez MCP

Agent może sam odpowiadać na pytania Retmana, co byłoby cichym zgadywaniem przez pełnomocnika.
Reguła: pytania są zwracane agentowi jako dane, ale każda wartość dostarczona przez agenta jest
zapisywana ze źródłem `known` (przez `retman_plan(known=...)`) albo, przez `retman_answer`, ze
źródłem `user` **plus** `channel: "mcp"`, tak by pojawiła się w potwierdzanym planie, który człowiek
przegląda w kroku 2 powyżej. Bramka człowieka jest na *planie końcowym*, a nie na każdym pytaniu.
(Ostrzejsza alternatywa, jeśli testerzy jej nie polubią: pytania wyboru także przez elicitation —
ten sam prymityw; rozstrzygnąć na starcie 0.3.)

### 4.4 Dodatki do audytu (W-15) (0.3, addytywne; bez zmian istniejących kluczy)

`result.json` i `journal.jsonl` dostają: `channel` (`"cli"|"python"|"mcp"`), dla `mcp`:
`client` (`clientInfo.name/version` z `initialize`), `confirmation` (`{"method":"elicitation",
"at": ts}`), `command.origin = "agent"` (tekst „command” to parafraza agenta, a nie słowa
użytkownika). Udokumentować w tabelach ARCHITECTURE 5.4.

### 4.5 Prywatność i N-04

Klient-agent MCP jest usługą **niekonfigurowaną** w `retman.toml`: zwykle to model w chmurze.
Ujawniane dane = podsumowania planów, `result.json`, ścieżki plików. Wartości domyślne przy dodaniu
sekcji `[mcp]` w 0.3:

```toml
[mcp]
# Added in v0.3 (not in the v0.1 template: no unused keys).
transport = "stdio"             # only value in 0.3
confirmation = "elicitation"    # only value in 0.3; fail-closed (p. 4.2)
plan_ttl_seconds = 900
max_open_plans = 16
expose_command_text = false     # result.json/journal text of commands is hidden from the agent
                                # even when [output] journal_commands = true
```

Zasoby zwracają `result.json` z usuniętymi `command` i ścieżkami bezwzględnymi (ścieżki względne
względem projektu; por. ADR-010 „bez ścieżek lokalnych”). `retman doctor` (7.2) dostaje linię „MCP”:
SDK obecne/wersja, transport, ustawione `--project`.

### 4.6 Testy (offline, STANDARDS 6.3/10.4)

Użyć pamięciowego transportu SDK (`Client(server, elicitation_callback=...)`) z
`FakeDecisionBackend`. Warte zachowania testy kontraktowe: (1) brak skutku `retman_execute` bez
`accept` elicitation dla danego id planu; (2) klient bez elicitation → `confirmation_unavailable`,
nic nie wykonane, nic nie zapisane w wynikach; (3) słownik planu przysłany z `confirmed=true` nie
jest honorowany (tylko plany trzymane po stronie serwera); (4) `result.json` ujawniany agentowi nie
ma tekstu poleceń ani ścieżek bezwzględnych; (5) dziennik zapisuje `channel="mcp"` oraz decyzje
odmowy/anulowania.

## 5. Wpływ na pliki Retmana

v0.1 (teraz): **brak zmian w kodzie**. Tylko obserwacja: `Plan.from_dict` akceptujące `confirmed` to
ukryta luka W-05 dla każdego przyszłego adaptera HTTP/GUI/MCP (`retman/core/plan.py:152`);
rozstrzygnąć osobno (np. `from_dict` zeruje `confirmed`, chyba że przekazano jawną flagę zaufania)
przed API HTTP/GUI, nie blokuje v0.1.

v0.3 (planowane): `retman/mcp_server.py` (nowy), `retman/cli.py` (podkomenda `mcp`),
`retman/config.py` + `config_template.toml` (`[mcp]`), `pyproject.toml` (dodatek `mcp`),
`retman/core/journal.py` + `pipeline.py` (pola `channel`, `confirmation`, `command.origin`),
`retman/doctor.py` (linia MCP), `tests/` (4.6), `retman/i18n/pl.toml` (brzmienie pytania o
potwierdzenie, tekst `confirmation_unavailable`).

## 6. Dokumenty do zmiany teraz (tylko dokumentacja)

### 6.1 Nowy ADR-012 w `docs/DECISIONS.md` (wiersz indeksu + wpis; status `Przyjęta`, 2026-10-19)

Tytuł: „MCP: Retman woła narzędzia przez API Pythona; serwer MCP Retmana w v0.3”. Kontekst: Kartograf
0.8.0 (`kartograf-mcp`) i IMGWTools 3.0.0 (`imgw mcp`) mają serwery MCP; autor nie rozstrzygnął —
decyzję **powierzył badaniu** (2026-10-19, `docs/research/2026-10-19-mcp.md`), a rekomendacja stała
się decyzją. Opcje: a/b/c/d z werdyktami z p. 1. Decyzja: (a) w v0.1 i dalej; (b) odrzucona; (c)
v0.3 wg p. 4 raportu (rozszerzenie opcjonalne `retman[mcp]`, `retman mcp --project`, potwierdzenie
przez elicitation, zamknięcie awaryjne). Konsekwencje: bez zależności `mcp` w rdzeniu
(ARCHITECTURE 9.3); brak zmian w v0.1; rozszerzenie N-04 przy v0.3. Raport skopiowany do
`docs/research/2026-10-19-mcp.md` (ten plik).

### 6.2 Wyzwalacze ponownego rozważenia (b) — zapisać w ADR, nie jako pracę

- Narzędzie staje się dostępne **wyłącznie jako usługa** (np. serwer Hydrografa): preferować jego
  API REST/HTTP przez `httpx` (już w rdzeniu; IMGWTools ma REST `/api/v1`) zamiast MCP.
- Konflikty zależności wymuszają **środowiska per narzędzie**: preferować `subprocess` + CLI
  `--json` (`kartograf … --json`, `imgw …`, udokumentowane kody wyjścia i dokumenty
  `*-error/1`/`imgw-result/1`) zamiast MCP: te same dokumenty, bez SDK, lżej.
- Tylko jeśli oba zawiodą, a narzędzie wystawia *wyłącznie* MCP: klient MCP per handler, dodatek
  opcjonalny.

## 7. Ryzyka

1. Wsparcie klientów dla elicitation/MRTR z 2026-07-28 jest niesprawdzone [WNIOSEK]; jeśli dominujący
   klienci go nie mają, (c) degraduje się do „tylko podgląd” i jego wartość spada → zdecydować w 0.3,
   czy wydawać, po teście dymnym. Zamknięcie awaryjne oznacza brak utraty bezpieczeństwa, tylko
   mniejszą użyteczność.
2. SDK `mcp` jest w 2.3.0 (2026-10-02), młode i łamiące względem 1.x; pin `>=2.3,<3` jak w obu
   narzędziach. Waga zależności (+23 pakiety, koło `cryptography`, `pywin32`) akceptowalna tylko
   jako dodatek.
3. Wartości dostarczone przez agenta (4.3) opierają się na tym, że człowiek przeczyta długi plan;
   łagodzone znacznikami proweniencji w `plan.summary()` i ostrzejszą alternatywą.
4. Prywatność (4.5): teksty poleceń/ścieżki wyciekające do agenta w chmurze; domyślnie ukryte, ale
   agent z konstrukcji widzi też podsumowania planów.
5. Podwójna ścieżka: użytkownicy mogą uruchamiać `kartograf-mcp` bezpośrednio obok Retmana i
   omijać ślad audytowy — poza kontrolą Retmana; dokumentacja powinna mówić, że audyt obejmuje tylko
   operacje wykonane przez Retmana.
6. Drzewo robocze IMGWTools było w chwili badania na `fix/archiwista-compat` (zawiera merge
   `31e96fa` wersji 3.0.0, czyli to, co zmierzono); tagi v0.8.0/v3.0.0 niewypchnięte — liczby (29/37
   narzędzi, rozmiary w bajtach) mogą się nieco przesunąć przed wydaniem.
